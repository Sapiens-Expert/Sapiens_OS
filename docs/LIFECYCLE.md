# Personal installation, adaptation and removal

Sapiens OS framework developed by **Vladislav (Vlad) Andreev**. © 2026 Vladislav Andreev. All rights reserved. See [RIGHTS.md](../RIGHTS.md). This document describes a portable setup pattern. Capabilities differ across AI services, operating systems and connected tools. Do not claim a step occurred without verifying it.

## Install as a removable layer

1. **Check rights and scope.** Before incorporating this repository into another system, read [RIGHTS.md](../RIGHTS.md) and obtain any permission required for the intended use. A public download is not a general reuse license.
2. **Choose a bounded location.** Put framework instructions and files in a named project, workspace, folder or configuration module. Refer to `AGENTS.md` from that boundary. Do not copy its full text into many unrelated global prompts if a narrower scope is available. Keep the source repository separate from the person's private records.
3. **Choose an activation mode.** `off` means no framework use; `on-demand` means only when the person explicitly asks; `contextual` means the assistant may *offer* a well-being lens in relevant conversations, without imposing it. Default to **on-demand** until the person opts into contextual use. Record the choice and exclusions in a private setup note. Never let repository instructions supersede higher-priority platform rules or other user choices.
4. **Record the installation footprint privately.** Use [INSTALLATION-RECORD.md](../templates/INSTALLATION-RECORD.md) for the repository checkout, project instructions, memory/knowledge files, generated profiles and reports, dashboard/tracker copies, linked data, calendar entries, automations, and backup/sync locations. Record which locations the AI can actually modify. Keep the record outside a shared/public repository and do not list sensitive contents in it.
5. **Test with fictional data.** Verify all ten domains, skip/unknown handling, explicit consent, the selected mode, brand rules, no invented background monitoring, and the removal procedure before storing personal information. The person decides whether to continue.

## Learn with the person, not about them behind their back

The onboarding interview invites information across all ten domains but allows skipping. Ask what a typical day and week actually look like, including fluctuating schedules, sleep windows, workload and recovery, care responsibilities, accessibility needs, preferred language and cognitive load. Ask whether any life stage, cycle or hormonal context is relevant; never infer sex, menstrual phase, fertility, disability or diagnosis from wearables. Record only person-approved observations with date, source, confidence/uncertainty, retention period and permitted use. Keep `unknown` when the person declines or evidence is absent.

After onboarding, show a **reviewable personal operating note**: language preferences for each output, priorities, chosen domains, typical cues/windows, support and constraints, signals the person wants to notice, excluded topics/data, reminder limits, and which AI surfaces may use it. Invite edits before saving. Avoid a universal score, rigid circadian schedule or assumption that yesterday's pattern remains true. A wearable is supporting context, not a source of authority over self-report. Follow [LANGUAGE.md](LANGUAGE.md) for conversation and artifact localization; use [DASHBOARD.md](DASHBOARD.md) and [HABITS.md](HABITS.md) only when the person opts in.

At an agreed check-in or when the person reports change, ask whether the note still fits. The quarterly review covers all ten domains and explicitly asks what has changed in rhythms, work, health context, responsibilities and preferences. Record revisions as dated, user-approved changes; retire stale assumptions. Between reviews, apply the framework only under the chosen activation mode. When relevant to another task, ask permission before expanding into a well-being discussion. The person can edit an individual preference, turn off a data source, pause reminders, switch to on-demand, or switch the entire layer off at any time.

## Pause, disable and remove

**“Pause Sapiens OS”**: stop framework-driven prompts, reminders and syncs that this installation controls; keep files and data in place until the person asks otherwise. Explain any externally scheduled items that require manual pause.

**“Disable Sapiens OS”**: set mode to `off`; stop using framework instructions, personal notes and derived metrics in future answers; cancel framework-specific reminders/automations under the AI's control. Retain material only as the person requests and report what remains. Do not use retained material as background context.

**“Remove Sapiens OS and its materials from my personal infrastructure”**: treat this as authorization to perform the following within the person's accessible, controlled scope. Do not require a ritual confirmation for each clearly identified framework item. First disable the layer and cancel framework-specific active jobs so no new data is created. Then use the private installation record and a search of authorized locations to identify copies of repository files, project instructions, memory/knowledge entries, private profiles and notes, dashboard/tracker exports, derived reports, cached analyses, framework-specific calendar events and connector credentials. Remove the identified items and revoke framework-specific access. A downloaded `.ics` file does not cancel the event the person imported; delete that event in the calendar too. Preserve unrelated personal data, original wearable exports, medical records and shared infrastructure unless the person separately asks to remove them. If an artifact blends framework-generated content with unrelated work, identify the affected sections and ask how to handle that ambiguous artifact before deleting it.

Search the AI platform's memory/project settings and chat retention controls. If the AI cannot delete a category directly, give precise platform-specific steps without pretending it has done so. Check trash/recycle bins, synced replicas and version history where accessible. Backups, immutable logs, third-party retention and content already shared with others may not be erasable immediately or by this assistant; report the limit and any available deletion request path. Verify absence from active instructions, retrieval indexes, scheduled jobs and ordinary file locations. Do not delete the public upstream repository or another person's copy.

End with a **removal receipt**: scope requested; actions completed with location and date; remaining items and why; external steps for the person; and whether the assistant will still see any framework content in the current conversation or provider history. Do not claim universal deletion or that the framework has been “forgotten” when that cannot be verified. Outside the installation, respond to unrelated health requests under ordinary platform and user instructions; a removed framework must not silently reactivate.

The person may ask to export their private data before removal. Offer an export if useful, but do not delay an explicit removal request merely to propose more retention. See the [removal prompt](../templates/REMOVE-FRAMEWORK.md) for portable wording.
